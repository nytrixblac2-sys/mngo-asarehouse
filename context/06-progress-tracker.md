## Architecture Decisions

1. **Owner preview is client-side only.** The Supabase session is not modified during preview. The preview user is stored in Zustand and cleared on sign-out. Server-side role enforcement always uses the real authenticated user, not the preview user.

2. **Financial calculations run client-side.** The API returns raw booking and expense records. Allocation splits, running balances, and fund summaries are calculated in `lib/financials.ts` on the client from these raw records. Only `prev_balance` is persisted as an aggregate.

3. **GHS and EUR never touch.** There is no conversion rate, no aggregated multi-currency total, and no combined balance anywhere in the codebase. Each currency has its own income rows, expense rows, and running balance.

4. **`canEdit` is the single access gate in components.** All edit controls check only `canEdit`. The role check that produces `canEdit` happens once at the App root. Individual components never inspect `currentUser.role`.

5. **Management fund data excluded server-side.** API routes check the requesting user's role before including Oak & Co. fund data in responses. Client-side `canEdit` gates the tab rendering, but the data exclusion is enforced independently at the API layer.

6. **Tailwind v4, not v3.** The architecture doc doesn't pin a Tailwind major version. The `shadcn` CLI available at scaffold time (`shadcn@4.16.0`) generates Tailwind v4 + `@base-ui/react` components (`@theme`, `@custom-variant`, `in-*`/`has-*` selectors) — incompatible with Tailwind v3's `@tailwind` directive model. Upgraded the project to Tailwind v4 (`tailwindcss@4`, `@tailwindcss/postcss`) to match, rather than fighting the current shadcn/ui ecosystem.

7. **Expense category `MANAGEMENT`, not `OAK_CO`.** The mockup's data layer uses `oak_co` as the literal category key, but `02-architecture-context.md`'s Financial Calculation Model and `01-project-overview.md` both use the generic term "management" throughout — Oak & Co. is described as *the reference implementation*, i.e. one workspace's display name, not part of the product's own vocabulary. The schema enum is `ExpenseCategory { OWNERS OPERATIONS MANAGEMENT }`; "Oak & Co." only ever appears as UI copy/workspace name, never as a stored value.

8. **Every child table carries a denormalized `workspaceId`**, not just `propertyId`. `03-code-standards.md` "API Routes" frames ownership checks as "verify `workspace_id` matches the authenticated user's workspace" per record — denormalizing avoids requiring a join through `Property` for every Row Level Security policy and API check.

9. **Money is `Decimal(10,2)`, not `Float`; all primary keys are `Uuid`.** Not specified in the context docs, but standard practice for financial data (avoids floating-point rounding) and keeps IDs consistent with Supabase Auth's own `auth.users.id` (UUID) for the `User.authId` foreign key.

10. **Prisma 7 requires a driver adapter — `@prisma/adapter-pg`.** Prisma 7 dropped the bundled native query engine for SQL databases; `PrismaClient` must be constructed with a driver adapter (`new PrismaPg({ connectionString })`) rather than a bare datasource URL. This also means `prisma.config.ts` (used only by the CLI for `migrate`/`studio`) and `lib/prisma.ts` (used by the running app) now hold their connection strings independently — `prisma.config.ts` has no `directUrl` slot in the installed `@prisma/config` version, so the CLI is pointed at `DIRECT_URL` directly and the app's own adapter is pointed at pooled `DATABASE_URL` separately.

11. **`Workspace.accountOwnerId` is nullable.** `User.workspaceId` (required) and `Workspace.accountOwnerId` (originally required, unique) reference each other, so neither row can be inserted first. Made `accountOwnerId` nullable and split creation into three steps (create workspace → create owner user → set `accountOwnerId`) in `prisma/seed.ts`; the same three-step order applies to the real "Kwame signs in and creates a workspace" flow (`01-project-overview.md` Core User Flow step 1) once auth is built. The API layer must guarantee `accountOwnerId` is never left null after bootstrap completes.

13. **RLS is a public-API safety net here, not the primary access-control layer — this qualifies a stated invariant.** `02-architecture-context.md` says "Row Level Security in Supabase enforces workspace scoping at the database layer — no query can return data from another workspace regardless of application-layer bugs." That's true for architectures where the app queries Postgres through Supabase's `anon`/`authenticated` roles (e.g. calling `supabase.from(...)` directly). This app doesn't: all data access goes through **Prisma**, connected as the `postgres` role via `DATABASE_URL`/`DIRECT_URL` — and Postgres RLS does not apply to the table owner, by design, regardless of policies. So enabling RLS (done in migration `20260730150106_enable_rls`, no policies defined) blocks Supabase's auto-generated public REST API from exposing any table to the `anon` key — a real, immediate hole otherwise, since that API exists for every `public` schema table by default — but it does **not** provide the "regardless of application-layer bugs" guarantee for Prisma's own queries. For this architecture, workspace/role scoping is enforced entirely by `app/api` route handlers (`03-code-standards.md` "API Routes": verify session, `workspace_id`, and role on every route) — a bug there **can** leak cross-workspace data; RLS will not catch it. Flagging this explicitly rather than leaving the stronger invariant unqualified — if per-request DB-level enforcement is wanted later, it would need a non-owner Prisma role plus session-scoped context (e.g. `SET LOCAL` per transaction), which is real infrastructure work, not a config toggle.

14. **Production login is sign-in only — the mockup's "Sign up" toggle was intentionally not built.** `01-project-overview.md`'s Core User Flow frames account creation as a specific, guided step ("Kwame signs in and creates a workspace for Oak & Co."), not public self-registration, and nothing in "Authentication and Roles" describes a signup form — only login, plus "magic link invites for property owners." A public signup form would also need to create a `Workspace` correctly (the same bootstrap-order fix from Architecture Decision 11), which is a distinct, larger feature. Logged as Open Question 7 rather than guessed at.

15. **Form validation/auth error text reuses shadcn's `--destructive` token.** `05-ui-context.md`'s color table has no error/failure color — understandable, since the mockup's "mock login" never fails. The login form needs to show "incorrect email or password" somehow. Rather than inventing a new hex value (against `03-code-standards.md`'s "never use hardcoded hex values"), reused the `--destructive` CSS variable already defined in `app/globals.css` for shadcn/ui's own primitives (`text-destructive` Tailwind class) — existing infrastructure for exactly this purpose, not a new design decision.

16. **`Pill` gained a `light` tone.** `05-ui-context.md` names five tones for `Pill` ("Six tones: accent, teal, amber, muted, light" — the doc says six but only lists five) while the mockup's actual `Pill` component only implements four (`muted`, `accent`, `teal`, `amber`; no `light`). Added `light` (white background, bordered, per the doc's "white bg" description) to `components/primitives.tsx` since it's explicitly named in the design spec even though unused so far — the mockup is authoritative for behavior, but this is an additive gap-fill, not a conflict.

17. **Each nav destination is a real Next.js route, not client-side view-switching.** The mockup is a single-page app: `nav` is React state, and Back/Forward replay an in-memory `navHistory` array rather than real browser history. None of the context docs specify a routing model explicitly, but `02-architecture-context.md`'s stack table names Next.js's "server/client boundaries, API routes, SSR" and "Default to React Server Components" — both presuppose real routes, not one client component switching on state. Built `app/(app)/{dashboard,bookings,issues,team,financials}/` as actual routes under a shared layout instead. The mockup's Back/Forward buttons are kept (`router.back()`/`router.forward()`) since real browser history now backs them for free — the mockup's custom history-array bookkeeping is no longer needed at all.

19. **Operational data (bookings/expenses/schedules/issues) goes through `app/api` + TanStack Query — not a Server Component's direct Prisma call, unlike properties.** `02-architecture-context.md`'s "Financial Calculation Model" is explicit: "The API returns full booking and expense records; the client computes allocations, running balances, and fund summaries dynamically" — that only works if the data actually arrives via a client-side fetch. Built `GET /api/{bookings,expenses,schedules,issues}` (workspace-scoped, property-scoped for `PROPERTY_OWNER`) and `lib/queries/*` (`useBookings`, `useExpenses`, `useSchedules`, `useIssues`) plus a `QueryClientProvider` in `app/providers.tsx`. `GET /api/expenses` is also where invariant #1 ("management fund data is never returned to property_owner sessions") actually gets enforced — verified live: Kwame (manager) sees all 8 expenses across 3 categories including `MANAGEMENT`; Prince (property owner) sees 4 rows, 0 of them `MANAGEMENT`. The one exception is `getVisibleProperties` in the App Shell layout (v1.0.0.6) — that stays a direct Server Component Prisma call, since it's one-time shell chrome, not data anything computes allocations/balances from.

20. **`effectiveUser`/`effectiveCanEdit` are threaded via a React Context (`components/effective-user-context.tsx`), provided by the already-client-side `AppShell`, not recomputed per page.** Discovered while building Dashboard: I'd initially had pages call `requireUser()` themselves and derive their own `canEdit`. That breaks the moment owner preview mode exists, because preview state is client-only Zustand and a Server Component page has no way to see it — it would keep showing the real manager's role even while "previewing as" an owner, contradicting `07-mockup.jsx`'s actual behavior (`{nav === 'team' && effectiveCanEdit && <TeamView/>}` — hidden during preview even for the real manager). Fixed the Team page stub to read `effectiveCanEdit` from context and render a fallback instead of a server-side redirect, since the gate now has to be able to change without a navigation. The real security boundary for Team's sensitive data was never the page-level check anyway — it's `GET /api/expenses`'s server-side `MANAGEMENT` category exclusion (Architecture Decision 19), which is unaffected by any of this.

21. **The Dashboard's expense chart is GHS-only, deviating from the mockup, which sums every expense's raw `amount` into one number regardless of currency.** That mockup behavior violates two "Do Not Change Without Explicit Instruction" invariants at once (`04-ai-workflow-rules.md`): it applies the 1.01 MoMo multiplier unconditionally instead of GHS-only, and it aggregates GHS and EUR into a single total, which `02-architecture-context.md` invariant #2 forbids outright ("There is no conversion or cross-account aggregation anywhere in the codebase"). Both bugs are invisible in the mockup only because Asare House's seed expenses happen to be 100% GHS. Fixed to filter to GHS only before summing (matching the chart's own "(GH₵)" label) and route the multiplier through `lib/financials.ts`'s `applyMomo`, which is itself currency-aware.

22. **`nightsBetween` (`lib/periods.ts`) does real date math, not the mockup's `dayOfMonth(checkOut) - dayOfMonth(checkIn)`.** The mockup's version silently breaks on any booking spanning a month boundary (e.g. Jan 30 → Feb 2 computes as negative, clamped to 0 nights). Occupancy would be quietly wrong for exactly the bookings most likely to matter. Not a product-behavior change, just correct date diffing.

24. **`Issue.status` is nullable.** The mockup's `IssueForm` sets `status: type === 'Note' ? null : 'Open'` — NOTE issues are informational and were never meant to enter the Open/In Progress/Resolved lifecycle (this also keeps them out of Dashboard's "open issues" banner, which filters on status). The schema originally had `status IssueStatus @default(OPEN)`, non-nullable — discovered as a real gap while building the issue-creation route, not a hypothetical. Migration `20260730163324_issue_status_nullable` fixes it; `lib/types.ts`'s `Issue.status` is now `IssueStatus | null`, and call sites where a prior filter already guarantees non-null (Dashboard's open-issues list) use a `!` assertion with a comment explaining why it's safe, rather than restructuring the filter into a type predicate.

25. **Route handler files (`app/api/**/route.ts`) only ever export HTTP method handlers — shared serialization/validation logic moved to `lib/{bookings,schedules,issues}.ts`.** Next.js's route module type contract rejects any other named export (`serializeBooking`, `bookingInputSchema`, etc., originally defined and exported directly from `route.ts` so sibling `[id]/route.ts` files could import them) — this surfaced as a real `tsc` failure, not a style preference. Each entity now has one `lib/<entity>.ts` holding its Prisma-row-to-DTO serializer and Zod input schema, imported by both the collection route and the `[id]` route, mirroring the existing `lib/properties.ts` pattern.

27. **`GET /api/team` is manager-only**, matching Property Owners' nav not showing Team at all (`05-ui-context.md`) rather than just hiding edit controls — this isn't about protecting sensitive data (names/roles aren't secret), it's consistency with the mockup's total-exclusion pattern for this specific screen. Built ahead of the Team screen itself because `ShiftForm`'s "Assigned to" picker (used from Bookings) needs the roster.

58. **PDF report generation happens entirely client-side, with no new API route** — reusing Architecture Decision 2 ("financial calculations run client-side") rather than qualifying it. The Financials screen already fetches every raw record (`bookings`, `expenses`, `manualIncome`, `team`, `workspace`) via TanStack Query; `lib/reports.ts`'s `buildMonthlyReport` filters those same arrays by month/property and feeds them through the *existing* `computeOwnersReport`/`computeManagementReport` (unchanged) — so the PDF can never drift from what the live screen shows, and there was no need to duplicate the role-scoping/serialization logic in a server route. `@react-pdf/renderer`'s `pdf(...).toBlob()` runs in the browser; the file downloads via a Blob URL and a synthetic `<a download>` click, never touching a server. The one place a server *would* matter — persisting a generated report for later retrieval (`02-architecture-context.md`'s "Storage Model" describes `reports/{workspace_id}/{month}.pdf` in Supabase Storage) — was deliberately not built: the user only asked to *generate* reports on demand, not to archive them, so adding Storage plumbing and a `Property`/`Report` schema field for it would be scope beyond the ask.
    Two real bugs were caught and fixed during verification, not just written and shipped: (a) react-pdf's built-in Helvetica font silently substitutes garbage glyphs for characters outside WinAnsi encoding — the cedi sign (₵) rendered as "µ" and the arrow (→) rendered as an apostrophe in an actual generated PDF, fixed with a PDF-specific `fmtCurrencyPdf`/`fmtAmount` ("GHS 1,234.56" instead of "GH₵1,234.56"; € was unaffected, it's in WinAnsi) rather than embedding a custom font for one glyph; (b) the recommendations engine's "largest single cost" callout for a spiking expense category was pulling from a combined Owners+Operations row list instead of filtering to the specific category, so it once named an Owners-fund payment ("Pam's Mum") as the cause of an Operations-category spike — fixed by adding a `category` field to `ReportExpenseRow` and filtering per-category before picking the top row.
    Two report types are independently selectable per generation (checkboxes, matching `07-mockup.jsx`'s `GenerateReportModal` exactly) rather than always bundling both: "Owner Report" (Owners + Operations funds, the owners' running balance held by the management company, itemized income/expenses — safe to send to Prince/Pamela) and "{Workspace} Internal Report" (management fund, team payments — manager-only, matches the existing Oak & Co. Internal tab's data boundary). The whole "Generate report" feature — both the Financials-screen button and the top-bar/sidebar entry points ported from the mockup — is gated on `effectiveCanEdit`, since `01-project-overview.md`'s Core User Flow frames report generation as something a manager does *for* owners ("Kwame generates a monthly owner report for Prince and Pamela"), not something owners trigger themselves.
    Month/Year `<select>`s replace the mockup's free-form From/To date inputs, matching the Financials/Bookings screens' own existing month-switcher pattern rather than introducing arbitrary date ranges the underlying month-scoped formulas were never designed to answer correctly.

60. **`bookingCoversDay` compares full ISO dates, not bare day-of-month numbers — the same class of bug Architecture Decision 22 already fixed for `nightsBetween`, just never applied here.** Found live, 2026-08-04: the user noticed Patricia Derrick's booking (checkIn `2026-06-19`, checkOut `2026-07-03`) had correct dates in its detail view but never appeared on the Month/Week/Day calendar grids. Root cause: `bookingCoversDay(b, day)` computed `s = dayOfMonth(checkIn)` (19), `e = dayOfMonth(checkOut)` (3), and checked `day >= s && day < e` — i.e. `day >= 19 && day < 3`, true for no day at all, for any booking whose checkout day-of-month is numerically less than (or equal to) its check-in day-of-month, which happens on every single booking that crosses a month boundary. The four call sites (`month-view.tsx`, `day-view.tsx`, `week-view.tsx`, `day-summary-panel.tsx`) each papered over this with a `dayOfMonth(b.checkIn) === day` OR-fallback, which only rescues the single check-in day — every other night of the stay, in either month, still didn't render — and `day-summary-panel.tsx`'s extra `dayOfMonth(b.checkOut) === day` fallback had the opposite problem: a real false-positive risk (a booking checking out in a *different* month/year could coincidentally match the currently-viewed month's day-of-month number and wrongly show a "Check-out" pill there). Fixed by giving `bookingCoversDay` the active month/year context and comparing full ISO date strings (`isoDateForDay(activeMonth, day) >= b.checkIn && ... < b.checkOut`) — correct for any date range, no fallback needed. Audited every other `dayOfMonth(...)` comparison in the codebase for the same risk (`04-ai-workflow-rules.md`'s "check if similar appear"): schedule/issue single-date comparisons are safe (their arrays are pre-filtered to the active month by `bookings/page.tsx`'s `monthShifts`/`monthIssues`, so day-of-month is unambiguous there), but `components/bookings/per-stay-view.tsx`'s "Add schedule"/"Log issue" buttons had the identical bug from a different angle: `onSchedule(dayOfMonth(b.checkIn))` passed a bare day number that `bookings/page.tsx`'s `openSchedule` then re-anchored to *whichever month is currently being viewed* — wrong whenever a booking is in Per Stay view's list only because its *checkout* matches the active month (its actual check-in is a different, earlier month). Fixed by widening `onSchedule`/`onLogIssue` to accept a full ISO date directly (`onSchedule(b.checkIn)`) alongside the existing day-number calling convention used everywhere else (grid-cell clicks, which are always genuinely within the active month already). Verified against live production data: 4 real bookings actually cross a month boundary (Priscilla Kumah Apr 29→May 3, Patricia Derrick Jun 19→Jul 3, Lutherking Dotse Jul 24→Aug 3, Victor Jul 31→Aug 1) — all four were affected. Confirmed the fix in a real browser (throwaway Co-Manager test account, same pattern as v1.0.2.6/v1.0.2.7): Patricia Derrick's booking now correctly shows a dot and appears in the day panel on June 19 (check-in), June 25 (mid-stay — previously invisible), and June 30 (previously invisible), screenshotted for visual confirmation, not just asserted from logs.

59. **The PDF report's optional "stated opening balance" override (v1.0.2.7) is a report-time-only input, not a reversal of Architecture Decision 31's "no manual `prev_balance` override field" ruling.** The user's concern, raised the same day: historical data is still being backfilled concurrently (see "Next Up" — the April Cleaning bill entries are still pending), so a report generated today calculates its running balance assuming `prev_balance = 0` plus *whatever's been entered so far* — which understates or overstates reality if entry is incomplete. The fix is scoped narrowly on purpose: `lib/reports.ts`'s `buildMonthlyReport` takes an optional `openingBalanceOverrides` (per-currency, per-fund) that substitutes for `property.prevBalanceGhs`/`prevBalanceEur` *only inside that one generation call* — never written to the database, never touching the live Financials screen. Explicitly considered and rejected: persisting it to `Property.prevBalanceGhs`/`prevBalanceEur` directly from the report modal, which would have silently changed the Financials screen's numbers for every month view (that field isn't month-scoped — see Architecture Decision 32) and blurred the line with the still-unbuilt, deliberately-explicit "Close month" action. When an override is supplied, `buildRecommendations` also skips the month-over-month balance-delta comparison for that fund/currency (comparing an overridden absolute number against a non-overridden prior month would itself produce a misleading recommendation) and the PDF's balance card gets a visible "based on an opening balance you stated" note — transparency for whoever reads the report, since the number is partly the preparer's word, not purely system-derived. Verified against live data: overriding GHS Owners to 10,000 and Management to 500 for July 2026 shifted both running balances by exactly the override delta, left EUR completely untouched (override was GHS-only), and the recommendation text switched to the stated-balance phrasing instead of a (now-meaningless) "grew/decreased by X" comparison.

61. **The Owner Report's EUR section discloses Oak & Co.'s management-fund figures (allocation, running balance) — a deliberate, narrow exception to invariant #1 ("management fund data is never returned to property_owner role sessions"), not a violation of it.** User decision, 2026-08-04, after comparing v1.0.2.6's fund-card layout against the report structure they'd used before this feature existed ("this was saying more"). The real-world payment flow only fully surfaced in this conversation: EUR (Airbnb) bookings are paid out to the *owner* directly, not to Oak & Co — the opposite custody direction from GHS/local bookings, which Oak & Co already collects and holds (matching the existing "Owners Running Balance held with management — GHS" wording, which is only accurate for GHS). That means the owner is the one who owes Oak & Co money in EUR, not the other way around, and the owner has no way to know how much without seeing Oak & Co's EUR allocation figure. The exception is narrow and stays server/data-model-safe: (a) it's GHS/EUR-asymmetric — GHS shows no Oak & Co figures anywhere in the Owner Report, only EUR does, matching the actual custody asymmetry; (b) it's bottom-line only, per explicit user choice — the Owner Report's EUR section shows Oak & Co's allocation % and final transfer amount, never the itemized team-payment breakdown, which stays exclusively in the "Oak & Co. Internal Report" checkbox's section; (c) it happens entirely within the already-manager-gated Generate Report feature (Architecture Decision 58 — `effectiveCanEdit`-only, and the PDF is generated client-side from data the manager's own session already legitimately has), so no API route or server-side check is weakened — this is a decision about what a manager *chooses to compile* into a document for the owner, exactly matching `01-project-overview.md`'s Core User Flow step 10 ("Kwame generates a monthly owner report for Prince and Pamela"), not a new data-access path. Also restructured the rest of the Owner Report to match the user's requested narrative order — income overview (both currencies together) → balance carried forward (shown explicitly via `OwnersReport.prevOwners`/`ManagementReport.prevManagement`, not folded silently into one final number) → income allocation (now shows the actual percentages via a new `allocationPct` field on `CurrencyMonthFigures`, not just amounts) → itemized income/expenses → the EUR transfer callout → a "final balance calculation" shown as worked arithmetic (opening + allocations − expenses = ending), not just the answer. No new financial calculations were needed for any of this — `lib/reports.ts`'s existing `computeOwnersReport`/`computeManagementReport` outputs already contained every figure required; this was purely a presentation restructure in `components/report-pdf-document.tsx`. Also fixed a second glyph bug caught in the same review: `lib/reports.ts`'s MoMo-fee recommendation still hardcoded "GH₵" (Architecture Decision 58 only fixed the PDF template's own currency formatter, not this one hardcoded string), rendering as "GHµ58.54" — fixed to "GHS 58.54". Verified against live data via the real Generate Report UI (throwaway test account, same pattern as prior stages): the rendered PDF's Oak & Co EUR transfer figure (€322.34) exactly matches the Oak & Co Internal Report's own EUR running balance for the same month, confirming the two are reading the same underlying number rather than a duplicated/diverged calculation.
